## 5교시 · 설정 파일이 고장 나도 거부하기

### 문제 5-1 · 설정 파일을 안전하게 읽는 함수 `load_json` 만들고, 고장 두 가지로 시험하기

- (가) 실행한 출력 전체를 붙여 넣고, 경고 두 줄이 각각 어떤 오류 때문에 나왔는지 적어 주세요.
  - 쓸 내용: ① 출력 전체 ② 경고 두 줄이 각각 어떤 오류 때문에 나왔는지
  - 답: 첫 경고 `[경고] 설정 파일 없음: config/users_typo.json` 은 그 이름의 파일이 없어서 `open` 에서 `FileNotFoundError` 가 나 `except FileNotFoundError:` 로 넘어간 것입니다. 둘째 경고 `[경고] 설정 파일 깨짐: config/users_broken.json` 은 파일은 있지만 마지막 항목 뒤에 쉼표가 남아 JSON 규칙이 틀려서 `json.load` 에서 `json.JSONDecodeError` 가 나 `except json.JSONDecodeError:` 로 넘어간 것입니다. 두 경우 모두 프로그램은 멈추지 않고 기본값 `{}` 를 받아 「사용자 0 명」으로 이어졌습니다.

```
config/users.json -> 사용자 6 명을 읽음, 판정을 계속한다
[경고] 설정 파일 없음: config/users_typo.json
config/users_typo.json -> 사용자 0 명, 등록된 사용자가 없다
[경고] 설정 파일 깨짐: config/users_broken.json
config/users_broken.json -> 사용자 0 명, 등록된 사용자가 없다
```

- (나) 🔍 실패했을 때 프로그램을 멈추지 않고 빈 설정을 리턴하는 것이, 오류로 멈추는 것보다 왜 안전한가요? 「멈춘 뒤 현장에서 생기는 일」을 넣어 적어 주세요.
  - 쓸 내용: ① 빈 설정을 리턴하는 이유 ② 멈춘 뒤 현장에서 생기는 일
  - 답: ① 빈 설정 `{}` 은 사용자가 한 명도 없는 상태라서, 판정 함수 `check_permission` 이 맨 처음 「사용자 파일에 있나?」에서 모든 요청을 「등록되지 않은 사용자」로 거부합니다. 프로그램은 계속 돌지만 아무것도 열리지 않는 **닫힘 기본 값(fail-closed)** 이 되고, 경고가 남아서 무엇이 고장인지도 바로 알 수 있습니다. ② 반대로 오류로 멈추면 정산 포털이 판정 결과를 받지 못해 업무가 통째로 막힙니다. 월말처럼 급한 때에는 현장 담당자가 「일단 판정을 끄고 다 통과시키자」고 판정 기능을 꺼 버리기 쉽고, 그러면 퇴사자 · 권한 없는 사람까지 모두 열리는 **열림 기본 값(fail-open)** 이 됩니다. 결국 멈추는 쪽이 사람 손을 거쳐 더 위험한 「모두 허용」으로 이어지기 때문에, 멈추지 않고 모두 막는 쪽이 안전합니다.

- (다) 🔍 설정 파일이 깨져서 모두 거부되면 정산 업무가 멈춥니다. 운영자가 이 상황을 빨리 알고 복구하려면 판정 프로그램에 무엇을 더하겠습니까? 두 가지 이상 적고, 그중 가장 먼저 할 것을 고른 이유를 적어 주세요.
  - 쓸 내용: ① 더할 것 두 가지 이상 ② 가장 먼저 할 것과 그 이유
  - 답: ① (1) 경고를 화면에만 찍지 말고 로그 파일에 시각과 함께 남기고, 담당자에게 메신저 · 메일로 바로 알림을 보낸다. (2) 판정 프로그램이 지금 정상 설정인지, 빈 설정(기본 거부)으로 돌고 있는지 보여 주는 상태 확인 기능을 둔다. (3) 마지막으로 정상이던 설정 파일 사본(git 이력)을 보관해 두고 한 번에 되돌릴 수 있게 한다. (4) 설정 파일을 저장 · 배포하기 전에 `python -m json.tool` 같은 형식 검사를 자동으로 돌려 깨진 파일은 아예 반영되지 않게 한다. ② 가장 먼저 할 것은 **(1) 알림**입니다. 모두 거부되는 상태를 운영자가 모르면 현장에서는 「갑자기 다 막혔다」는 문의만 쌓이고, 원인을 찾는 동안 「판정을 끄자」는 압박이 커집니다. 알림이 와서 「users.json 깨짐」이라고 바로 알면 복구(3번)나 원인 확인(최근 변경 이력)으로 곧장 갈 수 있어 업무가 멈춘 시간이 가장 많이 줄어듭니다.

## 6교시 · 테스트 케이스 설계

### 문제 6-1 · 꼭 지켜야 할 네 가지를 테스트로 설계하고, 팀원의 제안을 시험하기

- (가) `test_policy_extra.py` 를 실행한 출력 전체를 붙여 넣고, 실패한 줄 번호와 `AssertionError:` 뒤에 나온 글자를 적어 주세요.
  - 쓸 내용: ① `test_policy_extra.py` 출력 전체 ② 실패한 줄 번호 ③ `AssertionError:` 뒤의 글자
  - 답: ② 실패한 줄은 **14번째 줄**(6번 테스트의 `assert`)입니다. ③ `AssertionError:` 뒤의 글자는 「**6. 만료 정각에도 허용되어야 한다(팀원 제안)**」입니다. 5번 테스트(퇴사자는 예외가 있어도 거부)는 통과해서 `5 통과` 가 먼저 나왔습니다. 참고로 `test_policy.py` 는 `[경고] 설정 파일 없음: config/no_such.json` 다음에 `테스트 4개 모두 통과` 가 나왔습니다.

```
5 통과
Traceback (most recent call last):
  File "…/security-agent-toolkit/access_control/test_policy_extra.py", line 14, in <module>
    assert ok == True, "6. 만료 정각에도 허용되어야 한다(팀원 제안)"
AssertionError: 6. 만료 정각에도 허용되어야 한다(팀원 제안)
```

- (나) 🔍 그 실패는 코드가 틀렸다는 뜻인가요, 제안이 우리가 정한 만료 규칙과 다르다는 뜻인가요? 근거를 적어 주세요.
  - 쓸 내용: ① 코드가 틀렸는지, 제안이 정책과 다른지 ② 우리가 정한 만료 규칙과 3번 테스트 결과를 근거로 한 이유
  - 답: ① **제안이 우리가 정한 정책과 다르다**는 뜻이고, 코드는 틀리지 않았습니다. ② 3교시에 만료 규칙을 「지금 시각이 만료 시각보다 **앞**일 때만 유효, 만료 시각 정각에는 이미 거부」로 정했고, `find_exception` 은 그대로 `now < expires` 로 비교합니다. `test_policy.py` 의 3번 테스트도 17:59 는 「예외 1번」으로 허용, 18:00 은 거부를 기대했고 둘 다 통과했습니다. 즉 코드는 정한 규칙대로 18:00 을 거부했고, 팀원의 기대(18:00 허용)가 그 규칙과 반대라서 실패한 것입니다. 그래서 `<` 를 `<=` 로 바로 고치면 안 됩니다. 그러면 3번 테스트가 깨지고 정책이 알리지 않고 바뀝니다. 정각 허용이 정말 필요하면 정책 자체를 바꿀지 먼저 정하고, 정하면 코드 · 3번 테스트 · 설명 글을 함께 고쳐야 합니다.

- (다) 🔍 정책 코드를 바꿀 때마다 `test_policy.py` 의 1 ~ 4번 테스트를 돌리지 않으면 어떤 사고가 날 수 있나요? 네 개 중 하나를 골라, 그 테스트가 막아 주는 사고를 구체적인 장면으로 적어 주세요.
  - 쓸 내용: ① 고른 테스트 ② 그 테스트가 막아 주는 사고 장면
  - 답: ① **3번 테스트(만료 경계: 17:59 허용, 18:00 거부)** 를 골랐습니다. ② 장면: 팀원이 6번 제안을 듣고 「정각에도 되게 해 주자」며 `exception_policy.py` 의 `now < expires` 를 `now <= expires` 로 한 글자 고쳐 테스트 없이 반영합니다. 눈으로 몇 건 넣어 볼 때는 14:00 · 16:00 처럼 평범한 시각만 넣으니 아무 이상이 없어 보입니다. 그런데 이제 18:00 정각에 들어온 요청도 예외로 열리고, 나중에 비슷한 실수가 겹치면 끝난 예외가 계속 열려 있게 됩니다. 결국 「오늘 18시까지만」 준 정산 조회 권한이 약속한 시각을 넘겨 열려 있었다는 사실이 다음 날 로그 감사에서야 발견되고, 「예외 만료가 지켜지지 않았다」는 지적을 받습니다. 3번 테스트를 돌렸다면 고친 그 순간 `AssertionError: 3-2. 만료 정각 거부` 가 나서 반영 전에 바로 잡을 수 있었습니다.
